# Проверка валидатора ТЗ

Базовая версия — `11cd1c5`. Модель — `gemini-3.5-flash-lite`.

## Результат

Gemini вернул 35 из 48 запланированных полных отчётов. Для сравнения взяты 17 комбинаций «документ + формат + номер повтора» с результатами в обеих сериях. Базовый `subscription-pdf-2` сохранён, но исключён из сравнения до завершения соответствующего прогона после правок.

| Метрика на сопоставимых прогонах | До | После |
|---|---:|---:|
| Все эталонные находки | 10/16 | 15/16 |
| Находки на Markdown | 5/9 | 8/9 |
| Находки на PDF | 5/7 | 7/7 |
| Конфликт лимита и повторного SMS | 6/6 | 6/6 |
| Отсутствующая операция чтения подписки | 4/5 | 5/5 |
| HTTP 201 без условия возврата | 0/5 | 4/5 |
| Прогоны чистого кейса с лишним замечанием | 1/6 | 0/6 |

Выборка пока состоит из синтетических кейсов. Полное исходное ТЗ добавлено в запуск, но ни один из его 12 прогонов в этой серии не завершился. Незавершённые работы остановлены после ответа `429 RESOURCE_EXHAUSTED`. Диагностический ответ Gemini указал дневной лимит бесплатной квоты проекта в 500 запросов к модели и паузу `64225s`.

## Примеры

- Конфликт SMS. B003 говорит «Клиент получает не более одного SMS об опоздании на один заказ за календарный день». B005 требует отправить SMS «даже если сегодня уже отправляла SMS об опоздании по этому заказу». [Отчёт PDF](results/after/delivery-pdf-1.json)
- Пробелы API. В B003 заявлено «Экран при открытии читает сохранённую подписку через API», а B005 описывает `PUT /report-subscription` для замены подписки. В B007 заявлено «Успешными считаются HTTP 200 и HTTP 201», но внутри того же блока условие успеха описано только для `200`. [Отчёт Markdown](results/after/subscription-md-3.json)
- Ложное замечание. Новый проход пять раз пометил «Изменения экран сохраняет через API» как требование без реализации. Фильтр проверил явное описание `PUT /report-subscription`, которое заменяет тот же ресурс, и удалил эти находки, сохранив пробел по чтению. Один дубликат находки про чтение остался. [Отчёт с сохранённой отклонённой находкой](results/after/subscription-md-3.json)

Ответы Gemini для серии `after` получены с новым проходом инвентаризации API. Добавленный позже фильтр записи не меняет запросы к модели. Он повторно применён к этим отчётам командой `python tests/benchmark/recheck.py tests/benchmark/results/after`. Отклонённые замечания сохранены в `benchmark_filtered_findings`.

## Методика и повтор

Используется одно исходное ТЗ о расходах по карте и три синтетических кейса. Каждый представлен в Markdown и PDF. Для каждой комбинации кейса и формата выполняются три независимых полных прогона до правок и три после них. Модель задаётся через `GEMINI_MODEL` одинаково в обеих сериях.

| Кейс | Что проверяется |
|---|---|
| `requirements` | Месяц покупки, лимит push, операция чтения, условие HTTP 201 |
| `delivery` | Лимит SMS и повторная отправка после переноса срока |
| `subscription` | Операция чтения и условие HTTP 201 |
| `booking` | Контроль с явным исключением для администратора и описанными ответами API |

Эталон находится в [expected.json](expected.json). Находка засчитывается, если она есть в итоговом списке замечаний и её смысл совпадает с эталонным случаем. Несколько формулировок одного случая дают одно попадание. Предупреждения валидации цитат считаются отдельно. Для чистого контроля учитываются также локальные замечания. Метрики относятся к этому набору и к проверке замечаний по документу, а полнота извлечения отдельных требований не оценивалась.

Из корня репозитория, с установленными зависимостями бэкенда и ключом Gemini в окружении или `.env`:

```powershell
python tests/benchmark/run.py tests/benchmark/results/new --workers 2
python tests/benchmark/score.py
```

Для новой серии укажите новый каталог. При повторном запуске в тот же каталог раннер пропускает сохранённые результаты и восстанавливает ответы завершённых запросов внутри прерванного прогона. Флаги `--document` и `--repeat` позволяют повторить один прогон. Скрипт оценки использует ручную разметку сохранённых серий `before` и `after`.

После восстановления квоты для серии `before` загрузите пакет `validator` из ревизии `11cd1c5` через `PYTHONPATH`. Для серии `after` используйте текущую ветку. Повторите запуск с существующими каталогами результатов. Перед пересчётом разметьте новые итоговые замечания в `annotations.json`.
